# FastF1 전처리 (담당 A)

역할: FastF1에서 위치(X,Y,Z)·차량 스트림을 받아와 TUMFTM 레이스라인과 같은 거리축 `s`로 정렬한 뒤
인터페이스 **I0** (`fastf1_<track>.csv`)로 내보낸다. 이후 파이프라인은 전부 MATLAB/Simulink — 파이썬은
여기서 끝. **시나리오 A/B 분기는 블록 1(MATLAB)에서 처리하므로 I0은 시나리오와 무관하게 한 번만 만든다.**

## 설치

```
pip install fastf1 numpy pandas scipy
```

## 실행

TUMFTM Spa 레이스라인은 `data/tracks/tumftm/`에 포함돼 있어 따로 받을 필요 없다. 기본값은 2022 벨기에 GP
레이스(D9)이고 결과는 `data/raw/fastf1_spa.csv`로 나온다. F1 계정은 필요 없지만 FastF1 서버
(`livetiming.formula1.com`, `api.jolpi.ca`) 접속이 필요하다.

**결과 CSV는 레포에 커밋한다** (`.gitignore` 예외 처리됨). 블록 1은 이 파일만 읽으므로 FastF1 설치나 네트워크 없이
MATLAB 작업을 시작할 수 있다. 전처리 로직이나 `--z-rms`를 바꿨을 때만 다시 만들고 다시 커밋한다.

```
python python/fastf1_preprocessing/fastf1_to_csv.py
python python/fastf1_preprocessing/test_fastf1_to_csv.py
```

테스트는 합성 랩만 쓰므로 `fastf1` 없이 `numpy pandas scipy`만 있으면 돈다.

`--z-rms`는 z 평활 강도 [m]이다 (D6 민감도 파라미터, 기본 0.1).

## 처리 순서

1. 세션 로드, 캐시는 `~/.cache/fastf1`
2. 세이프티카·황색기·피트 입출구·1랩을 제외하고 107% 이내 랩만 사용
3. 위치 스트림(X,Y,Z, ~4.5Hz)과 차량 스트림(Speed/Throttle/Brake, ~4.2Hz) 보간 병합
4. 속도 적분 거리를 랩 길이로 정규화해 TUMFTM 레이스라인 거리 `s`로 정렬 (XY 좌표계가 다르므로 XY 정합 대신
   s 정렬 — 설계안 4.1절)
5. 여러 랩 평균 + 주기 평활 스플라인으로 고저 z(s) 추출 (노면 요철은 안 잡힘 — ISO 8608로 블록 1에서 별도 중첩)
6. 곡률 상호상관으로 타이밍 라인과 TUMFTM 시작점의 위상차를 구해 순환 이동 (Spa 16 m)
7. `fastf1_<track>.csv` 출력: `s, x, y, z, v, throttle, brake` (단위는 [02-인터페이스](../../docs/02-인터페이스.md))

## 블록 1에서 쓸 때

- `s`는 레이스라인(6938 m) 기준이다. 시나리오 B의 중심선(7000 m)에는 `s/6938.3*7000.1`처럼 비율로 옮긴다.
- `v`는 정상 랩 613개의 평균(레이스 페이스, 평균 114.4 s, 최속 109.354 s)이라 한계 주행 속도보다 낮다.
  W2 방법론 검증에서 랩 시뮬과 비교할 때 이 차이를 감안한다.

## 참고

- FastF1 문서: https://docs.fastf1.dev
- 여러 랩 겹치면 약 ±10m 오차 있음 (문서 명시) — 평균/평활로 흡수
- 가속도·서스펜션 채널은 없음 — 4Hz 속도 미분은 쓰지 말 것 (노이즈 큼)
- F1 데이터는 **서킷 형상(고저 z, 속도 비교)에만 쓴다** — 우리 차(BMW F82 M4급)의 하중 입력으로 F1 속도를
  직접 쓰지 않는다(차급 불일치, F1은 액티브 서스펜션 금지).

## 후속 과제 (부록, 당장 작업 아님)

Spa 파이프라인이 끝나고 여유가 있으면 블록 1만 교체해 뉘르부르크링 노르트슐라이페를 추가한다. I0 계약은

부록 참고.
